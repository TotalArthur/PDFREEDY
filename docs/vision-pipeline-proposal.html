Ref. 00
Premises

Two corrections to the brief before we start

Both change what gets built, so they belong up front rather than buried in a caveats section.

Correction 1 · Cloud OCR is ruled out by the constraint

The brief names AWS Textract, Google Cloud Vision, and hosted Donut/TrOCR. All three require uploading proprietary drawings to a third party and standing up a backend to broker it. You've confirmed drawings must stay on the machine, so none of them are on the table. Everything below is designed to hit the same objectives inside the browser. Where that costs us something real — and in one place it does — I say so rather than papering over it.

Correction 2 · The speed problem is ~50× worse than stated

The brief describes "multiple seconds per document." The actual figure in README.md is 1–2 minutes per large scanned sheet, and roughly 4× that with rotated-text scanning enabled. That isn't a polish problem, it's an architectural one — and it's good news, because a bottleneck that large has structural causes with structural fixes, not micro-optimisations.

What's actually causing it

Three things in the current code, all fixable:

  1. No parallelism. runQueue awaits one page at a time against a single shared Tesseract worker (ocrWorker). On an 8-core machine we're using one core.
  2. Whole-sheet OCR. Every page is rendered at OCR_SCALE = 3.5 and handed to Tesseract entire. A P&ID is mostly whitespace and line art; text occupies maybe 5–15% of the sheet. We're paying full price to recognise blank paper and pipe runs.
  3. Rotation by brute force. Vertical labels are caught by re-running the whole page at 0/90/180/270°, hence the 4× penalty and the reason the toggle ships off by default.

None of these need a server to fix. They need a different pipeline shape.

Ref. 01
Architecture

The proposed pipeline

Six stages. Stages marked in red are new; the rest are existing code, kept because they're already right.

S0

Content-addressed cache

SHA-256 the PDF bytes, key page results in IndexedDB by hash + pipelineVersion + settings. Re-opening a drawing you've already processed becomes instant instead of a full re-run — which today it always is.

Requires committing to hosted deployment (GitHub Pages or an internal static host). The README already notes file:// storage is unreliable across browsers; that's true of IndexedDB too. Still zero-install for users — just a URL instead of a double-click.

S1

Text layer extraction

Unchanged. getTextContent() with the transform matrix per run, giving correctly angled highlight boxes for free. Native CAD exports never touch the OCR path at all.

S2

Adaptive binarization

Unchanged, and it's the load-bearing piece the next stage depends on. The separable box-filter local threshold in preprocessForOcr already produces a clean binary plane; we're currently throwing it away after handing it to Tesseract.

S3

Text-region detection

Two-pass union-find connected-component labelling on that binary plane. Filter components by stroke geometry — size bounds, aspect ratio, fill density — to separate glyphs from line art, then cluster survivors into text regions and estimate each region's dominant orientation from its principal axis.

This is the single biggest change in the proposal, and it does two jobs at once: OCR runs on ~5–15% of sheet area instead of 100%, and rotation becomes per-region. A vertical line label gets rotated upright on its own, in one pass. The 4× rotated-text penalty disappears and the toggle can be deleted — vertical scanning becomes always-on and effectively free.

S4

Two-tier recognition

Tier A — Tesseract worker pool. Tesseract.createScheduler() with navigator.hardwareConcurrency - 1 workers, recognising region crops rather than sheets. Cropping also lets us drop from SPARSE_TEXT to SINGLE_LINE/SINGLE_WORD, which is more accurate per region because there's no layout ambiguity left to get wrong.

Tier B — transformer second opinion. Low-confidence crops only (expected 5–10%) get re-read by TrOCR-small-printed via transformers.js on the WebGPU backend. Strictly a re-reader on crops, never a page engine. See the risk note below.

S5

Lexicon-constrained resolution

Every read is resolved against the project line list and the nomenclature grammar before it reaches the index. This is where "smart guessing" actually happens — Ref. 02.

On Donut and TrOCR specifically

Donut is the wrong tool here. It's a document-understanding model built to read whole forms and receipts into structured output, at 200M+ parameters. We don't need document understanding — we need one short alphanumeric string read off a 200×40px crop. TrOCR-small-printed is ~60M parameters, ONNX-quantizable, and shaped exactly for that job. That's the one I'd carry into evaluation, and only as Tier B.

Ref. 02
Objective 2
Inference

Contextual inference, built on the line list

Your confirmation that line lists exist as spreadsheet exports is the most valuable input to this whole proposal. It converts the problem from open-vocabulary OCR — read arbitrary text off a degraded scan, which is hard — to closed-vocabulary matching — decide which of ~4,000 known strings this smudge most likely is, which is dramatically easier and far more defensible.

Import and grammar induction

Users import a line list CSV/XLSX per project. From it we derive two things:

  • The tag set — the finite list of strings that legitimately exist on this project.
  • A nomenclature grammar — tokenising the list into its positional fields (pipe size, fluid code, sequence number, spec class, insulation code) and learning the alphabet valid in each. This lets us validate and complete tags that follow project convention but aren't literally in the list yet.

Weighted resolution, reusing what's already there

The codebase already contains the key insight, in CONFUSION_OF: OCR failures on CAD callout fonts aren't random, they're a small set of physically indistinguishable glyph pairs. Today that drives a positional substring match. We promote it into the cost function of a weighted edit distance against the tag set — confusable substitutions near-free, everything else expensive.

OCR read V-68O1-l5PW4/3-75O-PPGO-RE1 Line list V-6801-15PW4/3-750-PP60-RE1 ← 4 subs, all confusable, cost 0.4 Runner-up V-6801-15PW4/3-750-PP60-RE7 ← 1 sub, NOT confusable, cost 3.0

The runner-up is a closer match by plain edit distance and the wrong answer. Confusion-weighting gets this right, and the existing tests/matching.test.js already pins down the principle — we're extending a proven mechanism, not inventing one.

Guesses must never look like certainties

The current tool has good discipline here — fuzzy matching off by default, GLYPH and FUZZY badges, OCR confidence always shown. Inference makes that discipline more important, not less. Three bands, surfaced in the UI:

Confidence banding
BandConditionPresentation
Confirmed Read matches a line-list tag exactly, or came from the PDF text layer Shown plainly, no qualifier
Inferred Resolved to exactly one tag under confusion-weighted distance, with a clear margin over the runner-up Badged, raw read shown alongside, one-click accept or reject
Ambiguous Two or more candidates within the margin, or grammar-valid but absent from the list All candidates listed with the crop; user picks. Never auto-resolved.
Ref. 03
Objective 3
Learning

The learning loop, scoped honestly

There's already a correction mechanism, and the README is admirably blunt that it's "a memorised dictionary, not machine learning" — fixing one O→0 teaches it nothing about O→0 anywhere else. That's the gap to close.

From dictionary to log

Replace the flat localStorage map with an append-only corrections log in IndexedDB, recording raw read, corrected value, region geometry, engine, tier, and per-character confidence. From that log we derive two things that do generalise:

  • A learned confusion cost matrix. Observed corrections update per-character substitution costs, seeded from the hand-authored classes. If your drawings' particular font confuses 4 and A, the system learns that from three corrections and applies it to every future sheet — which the current dictionary structurally cannot do.
  • Per-project tag priors. Tags corrected toward, or confirmed often, get a small prior boost in resolution.

Sharing learning without a server

Local-only means no shared database, so corrections would otherwise stay trapped on one laptop. Mitigation: export and import the corrections log as a JSON file that a team keeps on a network drive, with merge-on-import. It's manual where a backend would be automatic, and I'd rather name that plainly than pretend otherwise.

Limit · What "learning" cannot mean here

The brief says the model should improve over time. With no backend, model weights cannot be fine-tuned in the browser. What improves automatically is the inference layer — confusion costs, priors, tag sets. Genuine TrOCR fine-tuning on collected crops is an offline job on a workstation, shipping updated weights as a new static asset on a release cadence. That's a viable Phase 6+ if the corrections log shows enough volume to justify it; it is not something the loop does by itself.

Performance

Where the speed comes from

Four independent multipliers, three of which compound on first pass.

These are engineering estimates from the code structure, not measurements — which is exactly why the eval harness lands in Phase 1, before anything that claims a number. The target I'd commit to: a large scanned sheet from ~90s to under 10s on first pass, and near-instant on any subsequent open, with rotated-text scanning on by default throughout.

Search must be fast separately from extraction

Extraction speed and search speed are different problems, and "instantaneous search" is the one users feel most. Today runFullSearch walks every page's results on every query. We build a normalised trigram index over resolved tokens at ingest, so query cost scales with the number of matches rather than the size of the document — genuinely instant, and it stays instant on a 300-sheet drawing set.

One structural prerequisite

All of this roughly doubles the size of a file that is already 1,839 lines of HTML with inline script, and the tests currently lift functions out of it by name — which will not survive this. I'd split to ES modules with an esbuild step that still emits one deployable page. Users keep zero-install; we get real unit tests and a codebase that can absorb the change. This is a prerequisite, not a nice-to-have, and it's why Phase 1 opens with it.

Timeline

Rollout

Five phases over ten weeks. Ordered so the lowest-risk, highest-relief work ships first — the speed fix needs no ML at all and lands in a fortnight. Every phase ships something usable on its own; if the programme stops early, nothing is left half-built.

What each phase delivers

Phase 1 · Weeks 1–2 — Foundations

Module split and build step; IndexedDB content-hash cache; Tesseract worker pool; and a labelled ground-truth set of real sheets with an eval harness. Ships a 4–6× speedup and instant repeat opens with no accuracy change.

The eval set matters more than it sounds. There is no accuracy measurement in the project today, which makes every later claim unfalsifiable — including mine. Nothing after this phase gets merged without a number attached.

Phase 2 · Weeks 3–4 — Region detection

Connected-component analysis, region clustering, per-region orientation. The other large speed multiplier, and rotated/vertical text becomes on-by-default. Expected to increase recall on vertical line labels, since most users never turn the current toggle on.

Phase 3 · Weeks 5–6 — Line-list inference

CSV/XLSX import, grammar induction, confusion-weighted resolution, three-band confidence UI. This is the accuracy payload — the phase where "unable to find the line number" stops being the common outcome.

Phase 4 · Weeks 7–8 — Learning loop

Corrections log, derived confusion cost matrix, tag priors, export/import for team sharing. Migrates existing saved corrections rather than discarding them.

Phase 5 · Weeks 9–10 — Transformer tier

TrOCR-small-printed via transformers.js/WebGPU as a Tier-B re-reader, behind a feature flag, measured against the Phase 1 eval set.

Kill criterion · Phase 5

This is the highest-risk item and the one I'd cut first. It ships only if it clears +3 percentage points of tag recall on the eval set, with no first-pass regression beyond 2s per sheet, and a model download under 40MB. If it misses any of those, we keep the weights off and bank the phase as a documented negative result. By that point Phases 1–4 have already delivered every objective in the brief; Phase 5 is upside, not load-bearing.

Ref. 07
Decisions

What I need from you

  1. Hosted deployment — approve or reject. GitHub Pages or an internal static host. It's still zero-install for users, and it's what makes caching and saved corrections reliable. This is the only genuine dependency in Phase 1.
  2. A dozen representative sheets with known-correct tags. The eval set. Worst scans you have, not the best — the good ones already work. This gates every accuracy claim in the programme, mine included.
  3. One line list export in whatever form it comes out of your system, so Phase 3 is built against the real format rather than an assumed one.

With those three, Phase 1 starts immediately — and the speed problem, which is the one costing you time every day, is resolved inside two weeks regardless of how the rest lands.
